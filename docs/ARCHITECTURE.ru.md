# Архитектура

Этот документ описывает, как FOREST's Proxy Auto-updater устроен изнутри:
модули, потоки, состояние на диске, формат конфига, где лежат логи и как
работают балансировщик и проверки. Он написан для тех, кто читает или
сопровождает код. Пользовательское описание — в
[`../README.ru.md`](../README.ru.md).

Код — обычный Python и использует **только стандартную библиотеку**. Внешние
программы, на которые он опирается во время работы: `curl.exe` (все HTTP-пробы и
загрузка подписок), а также `PowerShell`, `tasklist`, `taskkill` и `netstat` для
запросов о процессах и портах в Windows.

## Карта модулей (`src/`)

| Модуль | Ответственность |
|---|---|
| `v2ray_updater.py` | Точка входа и CLI. Владеет циклом (`run_cycle`), стражем (`run_guard`), супервизором (`run_supervisor`), install/uninstall, статусом, диспетчером self-test и межпроцессным локом цикла. |
| `config.py` | Загрузка конфигурации и значения по умолчанию, определение каталога состояния, поиск ядра (`xray.exe`), определение режима клиента (standalone/v2rayN), прокси-цепочка для загрузки подписок. |
| `clientwrite.py` | Ядро клиентской логики: проверки связности/скорости, чёрный список, преобразование `Server`↔строка, JSON-хранилище серверов, генерация конфига ядра и конфига балансировщика, валидация конфига, файловые локи, **standalone-бэкенд** (свой процесс `xray.exe`, своё хранилище серверов, свой системный прокси через реестр WinINET), failover/страж, хранилище состояния и hot cache, а также **диспетчер режимов**, направляющий вызовы в бэкенд v2rayN при необходимости. |
| `clientwrite_v2rayn.py` | Бэкенд `v2rayn`: чтение/запись SQLite-базы v2rayN `guiNDB.db` и `guiNConfig.json`, резервные копии базы, активация по схеме stop→write→start→verify→rollback, страж, помощники GUI. Используется **только** при `client.mode == "v2rayn"`. |
| `clientwrite_posix.py` | POSIX-порт standalone-бэкенда (xray как служба `systemd --user`). В Windows не используется; оставлен для будущего порта на Linux. |
| `watch.py` | Сторожевой поток: быстрый локальный цикл, который держит ядро живым, замечает мёртвый порт, следит за пропускной способностью и «канарейкой» YouTube и запрашивает полный цикл при полном отказе. |
| `parser.py` | Разбор share-ссылок (`vless://`, `vmess://`, `trojan://`, `ss://`) в единый датакласс `Server`, а также обратное преобразование (`to_share_link`, `to_row_dict`). |
| `sources.py` | Источники подписок: поиск свежих репозиториев на GitHub, оценка свежести по sha1 содержимого, обновление фиксированных URL, кэширование тел источников на диск. |
| `xraytest.py` | Тестирование кандидатов через одноразовые экземпляры Xray: RTT, TCP-предфильтр, тест скорости, проба YouTube, финальная проверка, а также очистка осиротевших тестовых ядер. |
| `netfilters.py` | Отбор по разнообразию подсетей и фильтр диапазонов Cloudflare. |
| `tray.py` | Поток-потребитель трея. Визуальная иконка пока не реализована; поток читает канал статуса и пишет в лог изменения состояния. |
| `tray_status.py` | Канал статуса (`state/tray_status.json`): одно атомарное состояние + текущее описание процесса для будущей иконки в трее. |
| `i18n.py` | Минимальная таблица строк Русский/English и выбор языка. |
| `log.py` | Логгер: файл UTF-8 плюс безопасный для консоли вывод; выбирает каталог для лога, в который можно писать. |
| `selftest.py` | Набор self-test (`--selftest`): поверхность API, round-trip хранилища, генерация конфига, диспетчер режимов, i18n, конфиг при первом запуске, поиск ядра. Без сети, не трогает системный прокси, не занимает реальные порты. |

## Потоки

Один процесс (супервизор, `run_supervisor`) запускает четыре потока-демона:

| Поток | Цикл | Функция |
|---|---|---|
| `watch` | непрерывно, `watch.check_interval_s` | `watch.run_watch` — держит ядро живым, перестраивает пул за 1–2 с при смерти порта, следит за скоростью и YouTube; вызывает `full_cycle` при полном отказе. |
| `guard` | каждые 300 с | `v2ray_updater._guard_loop` → `run_guard` — один проход восстановления. |
| `update` | каждые 30 мин (если не задан `FOREST_NO_CYCLE`) | `v2ray_updater._update_loop` → `run_cycle` — полный цикл подбора. |
| `tray` | каждые ~2 с | `tray.run_tray` — читает канал статуса. |

Супервизор останавливается по `Ctrl-C`, по файлу `state/stop.flag` или по
истечении `FOREST_RUN_SECONDS` (используется тестами), после чего вызывает
`stop_core`.

`--watch` запускает сторожевой поток отдельно, как самостоятельный процесс
(защищён от дублирования через `state/watch.pid`).

## Цикл подбора (`run_cycle`)

1. Определить клиента (`config.find_client`) и потребовать ядро.
2. Проверить текущий активный сервер; запомнить здоровый baseline.
3. **Источники:** выполнить поиск на GitHub, если пришло время, обновить все
   известные источники, обновить фиксированные URL. Новые серверы дают только
   те источники, чей хеш содержимого изменился.
4. **Кандидаты:** разобрать изменившиеся источники, добавить собственные
   сохранённые серверы пользователя (они сохраняются и никогда не вытесняются
   автоматическими), устранить дубликаты; если пул мал, добрать его из кэша
   пула и кэшированных тел источников; ограничить сверху `test.max_candidates`
   (отдавая приоритет нескольким заведомо хорошим источникам).
5. **Фильтр Cloudflare:** отбросить узлы, чей адрес попадает в диапазоны
   Cloudflare (`netfilters.drop_cloudflare`).
6. **Тесты (`xraytest.run_tests`):** TCP-предфильтр → RTT по каждому кандидату
   (по одному одноразовому экземпляру Xray) → фильтр джиттера → фильтр
   `max_rtt_ms` → топ-`top_for_speed` с капом по разнообразию подсетей → тест
   скорости → фильтр `min_speed_kbps` → `final_verify` (RTT заново +
   доступность YouTube).
7. **Ранжирование:** по скорости (убыв.), затем по RTT (возр.); применить
   чёрный список; если пул ниже `reserve_min`, добрать серверы, прошедшие RTT.
8. **Кап по разнообразию:** не более `diversity.per_subnet_cap` серверов на /24;
   если из-за этого пул становится меньше `diversity.min_pool_after_cap`, кап
   ослабляется вплоть до `diversity.max_cap_relax`.
9. Обновить hot cache; записать `subscription_base64.txt`.
10. **Выбрать активный сервер:** оставить текущий, если он здоров и явно не
    проигрывает (`activation.prefer_current_if_healthy`), иначе — верхний в
    ранжировании.
11. Если прокси выключен вручную (`proxy_off.flag`), записать хранилище, но не
    активировать.
12. **Активировать** (`clientwrite.activate`): в режиме балансировщика поднять
    балансировщик; иначе записать конфиг ядра на один сервер и перезапустить
    ядро; затем при необходимости откатиться к аварийному пулу «последний
    рабочий».

Файловый лок (`state/lock.json`) не даёт двум циклам выполняться одновременно.

## Балансировщик и проверки

**Балансировщик.** В режиме балансировщика прошедшие серверы записываются в один
конфиг Xray функцией `build_balancer_config`: один inbound (mixed SOCKS/HTTP на
порту клиента) плюс второй SOCKS-inbound (`torrent-in`, `client.torrent_port`),
пул outbound'ов `proxy-out-*`, outbound `direct` (freedom) и `block`
(blackhole), `observatory`, который каждые 5 с проверяет здоровье пула, и
балансировщик `leastPing` с селектором `proxy-out`. Затем Xray направляет новые
соединения к живому узлу с наименьшим пингом **без перезапуска ядра**, поэтому
смерть одного узла не рвёт соединение. Правила маршрутизации: локальные имена →
direct, `torrent-in` → балансировщик, (опционально) домены/IP РФ → direct, всё
остальное → балансировщик. В пул входят только серверы с непустым паролем/ID
(пустой даёт невалидный outbound, который сломал бы весь конфиг).

**Защита конфига.** Перед любым перезапуском ядра новый конфиг валидируется
функцией `_validate_config`: он запускается на свободных эфемерных портах, пока
текущий конфиг ещё работает. Если он не поднимается, работающее ядро не
трогается. Хеш последнего успешно провалидированного конфига кэшируется, чтобы
идентичные конфиги не перепроверялись в течение часа.

**Проверки связности.** `probe_client` запрашивает
`https://www.gstatic.com/generate_204` (или эндпоинт Cloudflare при повторных
попытках) через локальный SOCKS-порт и в строгом режиме ещё скачивает данные с
`speed.cloudflare.com` и проверяет результат TLS verify — поэтому «пустышка»,
которая отвечает 204, но не несёт трафика, или сервер, подменяющий
TLS-сертификат, не принимается. `port_listening` — быстрая TCP-проверка,
используемая сторожем.

**Сторожевой поток (`watch.py`).** После каждого интервала проверки он заново
пробует порт с повторами; раз в несколько тиков заново проверяет системный
прокси, обновляет пул, пробует YouTube (3 неудачи → полный цикл) и измеряет
пропускную способность (2 медленных попадания → перестройка пула, иначе полный
цикл). Пока он спит, он смотрит за портом каждые 50 мс, поэтому мёртвое ядро
замечается за 1–2 с. Подряд идущие неудачи (`max_strikes`) или мёртвый порт
запускают перестройку балансировщика; если и это не удалось — полный цикл.

**Страж (`run_guard`).** Если прокси выключен вручную, он ничего не делает.
Иначе он пробует балансировщик, затем failover `guard_cycle` по сохранённым
`[AUTO]`-серверам (TCP-предфильтр, RTT, попытка по лучшим по очереди, чёрный
список для провалившихся), затем аварийный пул, затем полный цикл.

**Аварийный пул «последний рабочий».** `ensure_balancer` сохраняет последний
рабочий пул в `state/lastgood_servers.json`; когда живых серверов найти не
удаётся, `_emergency_restore` поднимает этот пул (с ограничением частоты — не
чаще одного раза в 120 с).

## Состояние на диске

По умолчанию всё лежит под `%LOCALAPPDATA%\ForestProxyUpdater`
(переопределяется через `FOREST_ROOT` или `paths.root`). Дерево исходников
остаётся чистым.

| Файл | Кто пишет | Содержимое |
|---|---|---|
| `config.json` | `config.load_config` | Рабочий конфиг (создаётся из `config.example.json` при первом запуске). |
| `logs/main.log` | `log` | Основной лог, UTF-8. |
| `state/servers.json` | `clientwrite` (standalone) | Своё хранилище серверов: `{next_index, active_id, servers:[...]}`. Автоматические серверы помечаются `[AUTO] `. |
| `state/forest_xray.json` | `clientwrite` | Конфиг нашего ядра. |
| `state/forest_xray.log` | ядро | Вывод нашего ядра. |
| `state/core.pid` | `clientwrite` | PID нашего ядра. |
| `state/state.json` | `StateStore` | Внутреннее состояние: hot cache, чёрный список, подпись/число/время балансировщика, метки последних проб, путь к гео-ассетам, хеш валидации, таймстемпы циклов. |
| `state/tray_status.json` | `tray_status` | Канал статуса для (будущей) иконки в трее. |
| `state/sources.json` | менеджер источников | Известные источники с их последним sha1, временем последнего успеха и счётчиками неудач. |
| `state/bodies/` | `sources` | Кэшированные тела каждого источника (разбираются заново без сети). |
| `state/pool_cache.json` | `v2ray_updater` | Недавние share-ссылки кандидатов. |
| `state/subscription_base64.txt` | `v2ray_updater` | Текущий пул как base64-подписка. |
| `state/lastgood_servers.json` | `clientwrite` | Последний рабочий пул (аварийное восстановление). |
| `state/proxy_orig.json` | `clientwrite` | Состояние системного прокси, сохранённое перед первым изменением. |
| `state/proxy_off.flag` | `clientwrite` | Присутствует, если прокси был выключен вручную. |
| `state/cf_ranges.json` | `netfilters` | Кэшированные диапазоны Cloudflare. |
| `state/lock.json`, `state/watch.pid`, `*.lock` | помощники локов | Межпроцессные локи и singleton сторожевого потока. |

Запись конфига и большей части состояния атомарна (файл `tmp` + `os.replace`).

## Формат конфига

Конфиг — это один JSON-объект. Отсутствующие ключи добираются из `DEFAULTS` в
`config.py`, поэтому частичный `config.json` валиден. При первом запуске без
конфига `config.example.json` копируется в `config.json`. Секции верхнего
уровня: `ui`, `client`, `cycle`, `test`, `sources`, `limits`, `activation`,
`watch`, `diversity`, `blacklist`. Разрешённый блок `paths`
(`root`/`state_dir`/`backup_dir`/`log_dir`) добавляется при загрузке и не
предназначен для ручного редактирования. Описание каждого ключа — в таблицах
[`../README.ru.md`](../README.ru.md#ключевые-настройки-из-configexamplejson).

## Два режима и диспетчер

`clientwrite._mode_of` определяет режим. `read_db_rows`, `write_auto_group`,
`read_active_id`, `write_active_id`, `activate`, `ensure_balancer`,
`guard_cycle`, `kill_kernels`, `start_client`, `stop_client`, `write_bin_config`
и `ensure_port_free` направляются в standalone-реализацию или в
`clientwrite_v2rayn` в зависимости от режима и от того, является ли путь к базе
SQLite-файлом `.db` (v2rayN) или нашим JSON-хранилищем. Остальная программа
общается только с этим диспетчером, поэтому оба режима делят `v2ray_updater.py`
и `watch.py` без изменений.

## Логи и диагностика

- Основной лог: `%LOCALAPPDATA%\ForestProxyUpdater\logs\main.log`. Если в этот
  каталог нельзя писать, логгер откатывается к каталогу `logs` рядом с кодом,
  затем к `%LOCALAPPDATA%\ForestProxyUpdater\logs`.
- Вывод ядра: `state/forest_xray.log`; вывод валидации:
  `state/forest_validate.log`.
- `--status` печатает режим, путь к ядру, запущено ли ядро, размер пула,
  состояние системного прокси и связность.
- `--dry-run` выполняет полный цикл, ничего не записывая и не запуская ядро.
